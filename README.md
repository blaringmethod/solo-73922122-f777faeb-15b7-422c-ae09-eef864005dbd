# 陶瓷质检迁库 · 试片复测记录对照页

陶瓷厂更换质检系统时，把新旧两套台账的试片复测记录接起来：上传两份同表头 CSV，
系统自动找出**合规且列数最少**的对照键，质检员复核登记同次/异次判定后，
按在用键配对并下载**含单边记录**的行号对照表。

技术栈：Flask + SQLite（标准库 sqlite3），Docker Compose 一键启动。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

不用 Docker 也可以本地跑：

```bash
pip install -r requirements.txt
DATABASE=./data/app.db python -m app.main     # 默认 5000 端口，PORT 环境变量可改
```

## 演示流程（选键 → 复核 → 停供/恢复 → 下载）

样例数据已生成在 `sample_data/`（旧表 200 行、新表 200 行；可由
`python3 scripts/make_sample_data.py` 重新生成）。

页面上依次操作（或跑自动演示 `python3 scripts/demo.py http://localhost:8000`）：

1. **上传**：选择 `old_system.csv`（旧系统）与 `new_system.csv`（新系统）。
   表头须完全一致，每份 ≤ 20000 行；新上传会重置整个会话并**换发会话标识**
   （`session_id`），此后旧页面/旧请求的一切操作都会收到「会话已过期」提示。
2. **勾选备选列**（至多 10 个）→ 保存 → 计算对照键。
   样例数据下得到两个单列键：`试片编号`、`条码号`
   （`窑炉/班次/日期/检验员` 重复不唯一，`备注` 有空值被"键列都须非空"排除）。
3. **选用「试片编号」** → 开始供数 → 下载对照表
   （100 行配对 + 100 行仅旧表 + 100 行仅新表）。
4. **复核登记同次判定**：旧表 101 行 ↔ 新表 1 行（P0101，两键值均相同）
   → 在用键仍合规，继续供数。
5. **复核登记异次判定**：旧表 150 行 ↔ 新表 50 行
   （试片编号同为 P0150，条码却不同 T-0150/T-9150）
   → 「试片编号」键失效，**保存判定的同时停供**，下载返回 409。
6. **撤销该判定**：键恢复合规，但供数不自动恢复（须重新选键）。
7. **重新登记该异次判定，另选「条码号」键** → 恢复供数；下载结果中
   P0150 按判定拆成 `T-0150 仅旧表`、`T-9150 仅新表` 两条单边记录。

## 规则与语义

- **合规键**：键列在两份表的每一行都非空；键列组合值在**每份表内**唯一。
  系统从 1 列起逐级搜索，列出**列数最少的全部**合规键（不返回更大的键）。
- **判定**（按两表数据行号登记，可撤销）：
  - 同次：两行的键值**须相同**；异次：两行的键值**须不同**。
  - 该规则定义为"键与判定集的兼容性"：违反任一判定的键即失效，
    不能选用、不能供数。同一对行重复登记（含改类型）须先撤销。
- **复核变动后更新候选，不重扫任一原表**：算键时为每个候选键存储
  `键 × 表 × 行 → 键值散列` 的投影（`projections` 表）；登记/撤销判定后
  只读投影与判定两张小表重算各键合规性，不触碰两份原始台账。
  （自动化测试里清空原表后复核更新照常工作，可证。）
- **供数状态机**：
  - 选用合规键 → 供数；复核后**在用键仍合规就继续供数**；
  - 在用键被判定失效 → 判定与"停供"在**同一事务**保存，下载立即 409；
  - 停供后**只能另选（或重选）合规键恢复**，键恢复合规不会自动复供。
- **保存失败回滚**：登记/撤销/停供在一个 SQLite 事务内提交，
  任一步失败整体回滚——**原判定与供数状态保持不变**（有专项测试模拟失败验证）。
- **下载**：按在用键全外连接两表，输出 `键列…, 旧表行号, 新表行号, 对照状态`
  （配对 / 仅旧表 / 仅新表），UTF-8 带 BOM，Excel 可直接打开。
- **会话标识与并发安全（重新上传是唯一有效会话）**：
  - 每次成功上传都在**同一事务**内换发新的 `session_id`（存 `meta` 表，
    与新台账同生共死），网页所有表单以隐藏字段携带、JSON API 以
    `session_id` 字段携带、下载链接以查询参数携带。
  - 备选列、算键、选键、判定、下载都先校验会话标识；所有**写操作在
    `BEGIN IMMEDIATE` 拿到写锁后再校验第二次**，封死"检查后、写入前"的
    并发窗口。因此即使在算键（可能耗时数十秒）进行中重新上传两份 CSV，
    旧计算也只会在提交时收到 409「会话已过期」并整体回滚，**旧列名、
    旧键、旧投影不可能写入新会话**。
  - 重新上传后，键、投影、表头、行数、判定、供数状态必然对应**同一份**
    新台账；旧页面选键或下载不再因旧列名触发 500，而是明确的 409 提示，
    刷新页面后按新台账重新计算即可。
  - 大台账算键的写事务（候选键 × 数万行投影）可能持锁较久，并发写请求
    排队等锁（`busy_timeout=60s`）；极端等锁超时时 API 返回 503、
    网页回显提示，而不是裸 500。

## JSON API（网页表单同一套逻辑）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/upload` | multipart 上传 `file_a`、`file_b`；响应含新 `session_id` |
| POST | `/api/columns` | `{"columns":[...], "session_id"}` 保存备选列（1~10） |
| POST | `/api/keys/compute` | `{"session_id"}` 计算列数最少的合规键（含投影） |
| POST | `/api/keys/select` | `{"key_id":N, "session_id"}` 选用并供数 |
| POST | `/api/judgments` | `{"row_a","row_b","type","session_id"}` 登记判定 |
| POST | `/api/judgments/revoke` | `{"id":N, "session_id"}` 撤销判定 |
| GET | `/api/state` | 会话全量状态（含 `session_id`、键合规性、判定、供数） |
| GET | `/download.csv?session_id=...` | 行号对照表；未供数/会话过期时 409 |

会话标识不匹配统一返回 `409 {"error": "会话已过期：…"}`；
缺少标识返回 400；写锁等待超时返回 503。

## 自测

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q        # 26 个用例
python scripts/demo.py            # 端到端演示（需服务已启动，含会话过期场景）
```

覆盖：上传校验（表头不一致 / 超 2 万行 / 列数不符）、备选列校验、
最小键计算（空值排除、单列不足时取两列、无合规键）、选键下载、
判定全流程（同次保持供数、异次致停供、换键恢复、撤销不自动复供）、
判定校验（行号越界 / 重复对 / 类型冲突）、**保存失败回滚**、
**清空原表后复核更新照常**（不重扫原表）、会话重置，以及竞态防护：
重新上传后旧 `session_id` 的全部写操作与下载一律 409、算键进行中重新
上传不污染新会话（多线程专项复现）、新会话键/投影/表头/行数/供数状态
对应同一份台账、网页表单 flash 提示、写锁排队与超时 503 兜底。

实测（本机，2 万行 × 2 表、10 个备选列）：上传 1.1s；无合规键时算键穷举
约 19s（纯读阶段）；存在 45 个两列键时算键含投影写入约 40s（其中投影写
事务约 36s）；下载 0.65s、单次复核重算约 10ms。并发写在 SQLite WAL 下
串行提交，长写事务期间其他写请求排队（`busy_timeout=60s`）。

## 已知限制 / 未完成

- 单会话：系统同时只维护一个对照会话，重新上传即重置（无多用户/多项目
  隔离）。`session_id` 只用于区分"重新上传前后的请求"，不是访问令牌——
  系统本身无登录鉴权，知道标识即可操作该单一会话。
- 判定只按行号登记，未做"同次判定须键值相同"的登记前硬校验——
  该约束以"键兼容性"语义落地（违反的键失效），与"复核可使键失效"的需求一致；
  登记响应会返回本次判定使哪些键失效，页面上也有提示。
- 键值投影存 64 位散列而非明文（复核只需判等）；下载时的键值取自原表。
- 未做登录鉴权与操作审计；CSV 解析假设逗号分隔、首行表头
  （UTF-8/GB18030 自动识别，单元格去首尾空白）。
- 本修复环境未安装 Docker 守护进程，无法实际执行 `docker compose up --build`；
  已用与 Dockerfile 完全一致的启动命令
  （`gunicorn --workers 1 --threads 8 app.main:create_app()`）在本机实测，
  含多线程网页竞态复现，`docker-compose.yml`/`Dockerfile` 无需改动即可使用。
